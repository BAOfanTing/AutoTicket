# AutoTicket 数据统计接口对接文档（极简版）

> 版本：v2.0
> 面向对象：服务端开发者
> 客户端：AutoTicket（Python GUI 版 / JS 命令行版 / 微信小程序版）

---

## 1. 需求

客户端界面上展示两个数字：

| 指标 | 规则 |
| --- | --- |
| **在线人数** | 打开软件 **+1**，关闭软件 **−1** |
| **抢到票数** | 抢到一次 **+1**，展示累计总数（区分 2 元 / 4 元 / 6 元） |

服务端不需要存任何账号信息，不需要定时任务，两个接口搞定。

---

## 2. 接口一：上线 / 下线

```
POST /api/v1/online
Content-Type: application/json
```

**请求体**

```json
{
  "client_id": "9f2c1e7a4b8d4f0e",
  "action": "open"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `client_id` | string | 是 | 客户端本地生成的随机匿名标识（UUID4 去横线），首次运行生成后存在 `config.json`。**不是手机号、不是 user_id** |
| `action` | string | 是 | `"open"` 上线 / `"close"` 下线 |

**响应**

```json
{
  "code": 0,
  "msg": "ok",
  "data": { "online": 12 }
}
```

**服务端处理逻辑**

- `action = "open"`：把 `client_id` 写入在线表（已存在则只更新 `last_seen`），返回当前在线数
- `action = "close"`：从在线表删除该 `client_id`，返回当前在线数
- **在线人数 = 在线表里的行数**

> 表用 `client_id` 做主键，同一个人开多个窗口只会算 1 个。

---

## 3. 接口二：抢票成功上报

抢到票时调用一次。客户端判定标准：响应解密后 `msg == "兑换成功"`（见 `JavaScript_Version/AutoTicket.js`）。

```
POST /api/v1/grab
Content-Type: application/json
```

**请求体**

```json
{
  "client_id": "9f2c1e7a4b8d4f0e",
  "exchange_id": "10"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `client_id` | string | 是 | 同上 |
| `exchange_id` | string | 是 | `"9"` = 2 元券，`"10"` = 4 元券，`"11"` = 6 元券 |

**响应**

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "total": 53,
    "by_type": { "9": 3, "10": 5, "11": 1 }
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `total` | 总抢到票数（三种券合计） |
| `by_type` | 各券种累计数，**固定返回三个键**，没有数据返回 `0` |

**服务端处理逻辑**

- 校验 `exchange_id` 必须是 `9` / `10` / `11` 之一，否则返回 `code: 400`
- 插入一条记录（`created_at` 用**服务端时间**）
- 返回最新总数

> 客户端上报失败会重试。**服务端用 `request_id` 幂等键去重**：客户端每次真实抢到票生成一个唯一 `request_id`，网络重试时复用同一个，服务端按主键只记 1 条。
>
> 这比早期的时间窗口方案（同一 `client_id` + `exchange_id` 60 秒内只记 1 条）更准确——时间窗口无法区分「同一张票重试」和「短时间内抢到多张票」，在 12 线程并发、0.15 秒间隔的场景下，2 秒内抢到 2 张同面额的券是可能的，会被错误吞掉。
>
> **老客户端兼容**：未携带 `request_id` 的请求仍走 60 秒时间窗口去重。

## 5. 数据库

```sql
-- 在线表：一行 = 一个在线的人
CREATE TABLE stats_online (
  client_id VARCHAR(64) NOT NULL PRIMARY KEY,
  last_seen DATETIME    NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 抢票记录表：只追加，不修改
CREATE TABLE stats_grab (
  id          BIGINT      NOT NULL AUTO_INCREMENT PRIMARY KEY,
  client_id   VARCHAR(64) NOT NULL,
  exchange_id TINYINT     NOT NULL,
  created_at  DATETIME    NOT NULL,
  INDEX idx_type (exchange_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**统计 SQL**

```sql
-- 在线人数
SELECT COUNT(*) FROM stats_online;

-- 总票数
SELECT COUNT(*) FROM stats_grab;

-- 各券种
SELECT exchange_id, COUNT(*) AS cnt FROM stats_grab GROUP BY exchange_id;

-- 去重检查（上报前查一次）
SELECT COUNT(*) FROM stats_grab
WHERE client_id = ? AND exchange_id = ? AND created_at > (NOW() - INTERVAL 60 SECOND);
```

### ⚠️ 唯一需要多写的一行

用户**强杀进程、断电、崩溃**时，客户端的"下线"请求发不出去，那个 `-1` 就丢了，在线人数会慢慢涨上去。

所以在 `action = "open"` 的处理里，顺手加一句清理：

```sql
DELETE FROM stats_online WHERE last_seen < (NOW() - INTERVAL 24 HOUR);
```

正常关闭仍然靠 `-1` 生效，这句只是给异常退出兜底。**一行 SQL，不需要定时任务。**

## 6. 参考实现（Node.js + Express + MySQL）

```javascript
const express = require('express');
const mysql = require('mysql2/promise');

const VALID_IDS = ['9', '10', '11'];
const pool = mysql.createPool({ /* 你的数据库配置 */ });
const app = express();
app.use(express.json());

// 参数校验：client_id 只允许字母数字下划线短横线，最长 64
const validId = (id) => typeof id === 'string' && /^[A-Za-z0-9_-]{1,64}$/.test(id);

async function getStats() {
  const [[{ online }]] = await pool.query('SELECT COUNT(*) AS online FROM stats_online');
  const [[{ total }]] = await pool.query('SELECT COUNT(*) AS total FROM stats_grab');
  const [rows] = await pool.query('SELECT exchange_id, COUNT(*) AS cnt FROM stats_grab GROUP BY exchange_id');
  const by_type = { '9': 0, '10': 0, '11': 0 };
  rows.forEach(r => { by_type[String(r.exchange_id)] = Number(r.cnt); });
  return { online: Number(online), total: Number(total), by_type };
}

// —— 上线 / 下线 ——
app.post('/api/v1/online', async (req, res) => {
  const { client_id, action } = req.body || {};
  if (!validId(client_id) || !['open', 'close'].includes(action)) {
    return res.json({ code: 400, msg: 'invalid params', data: null });
  }
  try {
    if (action === 'open') {
      // 兜底：清掉 24 小时没动静的异常退出会话
      await pool.query('DELETE FROM stats_online WHERE last_seen < (NOW() - INTERVAL 24 HOUR)');
      await pool.query(
        `INSERT INTO stats_online (client_id, last_seen) VALUES (?, NOW())
         ON DUPLICATE KEY UPDATE last_seen = NOW()`,
        [client_id]
      );
    } else {
      await pool.query('DELETE FROM stats_online WHERE client_id = ?', [client_id]);
    }
    const [[{ online }]] = await pool.query('SELECT COUNT(*) AS online FROM stats_online');
    res.json({ code: 0, msg: 'ok', data: { online: Number(online) } });
  } catch (e) {
    console.error('[online]', e.message);
    res.json({ code: 500, msg: 'server error', data: null });
  }
});

// —— 抢票成功上报 ——
app.post('/api/v1/grab', async (req, res) => {
  const { client_id, exchange_id } = req.body || {};
  const exId = String(exchange_id);
  if (!validId(client_id) || !VALID_IDS.includes(exId)) {
    return res.json({ code: 400, msg: 'invalid params', data: null });
  }
  try {
    // 去重：60 秒内同一个人同一个券种只记一次
    const [[{ dup }]] = await pool.query(
      'SELECT COUNT(*) AS dup FROM stats_grab WHERE client_id = ? AND exchange_id = ? AND created_at > (NOW() - INTERVAL 60 SECOND)',
      [client_id, exId]
    );
    if (dup === 0) {
      await pool.query('INSERT INTO stats_grab (client_id, exchange_id, created_at) VALUES (?, ?, NOW())', [client_id, exId]);
    }
    const stats = await getStats();
    res.json({ code: 0, msg: 'ok', data: { total: stats.total, by_type: stats.by_type } });
  } catch (e) {
    console.error('[grab]', e.message);
    res.json({ code: 500, msg: 'server error', data: null });
  }
});

// —— 查询统计 ——
app.get('/api/v1/stats', async (req, res) => {
  try {
    res.json({ code: 0, msg: 'ok', data: await getStats() });
  } catch (e) {
    res.json({ code: 500, msg: 'server error', data: null });
  }
});

app.listen(3000, () => console.log('stats service on :3000'));
```

## 7. 客户端调用约定

| 行为 | 时机 | 说明 |
| --- | --- | --- |
| `POST /online` `open` | 软件启动时 | 拿回在线人数显示在界面上 |
| `POST /online` `close` | 软件关闭时 | 窗口关闭事件 + 进程退出兜底各发一次，超时 1 秒 |
| `POST /grab` | 抢到票时 | 失败重试最多 3 次 |
| `GET /stats` | 界面刷新（每 60 秒） | **纯展示用，失败静默忽略** |

**关键：所有统计请求都不能影响抢票主流程。** 超时 3 秒即放弃，失败不弹窗、不写错误日志。

**压力估算**：100 人在线时，只有开/关软件时才有请求，加上每分钟 100 次只读查询，QPS 不到 2。随便一台小服务器都够。

## 10. 隐私说明

1. `client_id` 是客户端随机生成的匿名 UUID，与手机号、`user_id`、`login_name` **无任何映射关系**。请勿要求客户端上报手机号或真实姓名。
2. **本接口不做鉴权，是刻意选择**。客户端是分发出去的 exe，任何密钥都会被打包进去、可被直接提取，加了等于没加，只是多一层虚假的安全感。真正的防线是：60 秒去重 + 服务端对单 IP 做基础限流（例如同一 IP 每分钟最多 60 次请求，超出返回 429）。这两条挡不住恶意攻击，但足以挡住误用和好奇。
3. 票数由客户端上报，理论上可伪造。本项目是开源工具、用户是熟人圈子，上述措施已经够用。
4. **万一真被刷**：改掉接口路径（例如 `/api/v1/grab` → `/api/v1/g2`）并随新版本客户端下发即可，旧的 URL 自然失效。这是无密钥方案下的应急手段，所以请把接口路径当作可变更的配置项来写，不要散落在多处。
5. 若微信小程序端也要调用，该域名需在微信公众平台配置为 request 合法域名，且需已备案。

## 12. 实际部署记录（2026-10-17）

线上跑的不是第 5/6 节的 Node.js + MySQL 参考实现，而是 **Python 3.12 + SQLite，纯标准库，单文件**。

| 项 | 值 |
| --- | --- |
| 服务端地址 | `https://www.relx5th.space`（nginx 终结 TLS 后反代到本机） |
| 应用监听 | `127.0.0.1:8080`（不直接暴露公网） |
| nginx 配置 | `/etc/nginx/conf.d/autoticket-stats.conf`（备份 `/root/nginx-autoticket-stats.conf.bak`） |
| 证书 | `/etc/letsencrypt/live/www.relx5th.space/`，certbot 定时自动续期 |
| 程序文件 | `/opt/stats/stats_server.py` |
| 数据库 | `/opt/stats/data/stats.db`（SQLite，WAL 模式） |
| 服务管理 | `systemctl status autoticket-stats` |
| 第三方依赖 | 无 pip 包（nginx 是 apt 装的，只做反代和 TLS 终结） |
| 实测占用 | 应用内存约 22 MB，磁盘约 76 KB |
| 限流 | 单 IP 每 60 秒 120 次，超出返回 429 |

**为什么不用文档里的 Node + MySQL 方案**：这台机器访问 Docker Hub 的出口被限制（`dial tcp 199.59.148.102:443: i/o timeout`），几个国内镜像源对较大的镜像层都返回 502，装 MySQL 得反复绕。而且量级完全不需要 —— 100 人在线时 QPS 不到 2，SQLite WAL 绰绰有余，还省掉一个容器、少 200MB 镜像。

**接口契约**：路径、字段名、码值和本文档一致。差异有两处：一是抢票去重从「60 秒时间窗口」升级为「`request_id` 幂等键」（见下一节）；二是时间字段存 Unix 秒（`REAL`）而不是 `DATETIME`，避免时区与字符串比较问题，统计 SQL 语义不变。

### ⚠️ 抢票计数准确性（2026-10-18 修正）

早期版本的抢票计数会**少算**，两个原因：

1. **客户端主动合并**：`AutoTicket.py` 里有 `_grab_reported` 标记，一轮任务（`job()`）内只上报 1 次。而一轮会开 12 个并发线程、间隔 0.15 秒，2 秒内抢到 2 张同面额的券完全可能，第 2 张被吞掉。**已移除该标记，每张票都上报。**
2. **服务端时间窗口误伤**：60 秒窗口无法区分「同一张票重试」和「抢到多张票」。**已改为 `request_id` 幂等键。**

数据库变更：

```sql
ALTER TABLE stats_grab ADD COLUMN request_id TEXT;
CREATE UNIQUE INDEX idx_grab_request ON stats_grab(request_id);
CREATE INDEX idx_grab_exchange ON stats_grab(exchange_id);
```

老数据回填为 `legacy-<id>-<rand>`，不参与新的幂等判断。备份在 `/root/stats-backup-20261018-140253.db`。

三种场景的验证结果：

| 场景 | 期望 | 实测 |
|---|---|---|
| 2 秒内抢到 2 张同面额 | +2 | +2 ✓ |
| 同一张票重试 4 次 | +1 | +1 ✓ |
| 5 张票并发上报 | +5 | +5 ✓ |
| 不带 `request_id`（老客户端） | 60 秒窗口去重 | +1 ✓ |

### ⚠️ 备案是硬门槛（大陆服务器）

未备案域名挂在大陆服务器上时，中间设备会按 **SNI 直接 RST 掉 TLS 握手**，HTTP 也会被改写。现象是服务器上一切正常、外面连域名就是不通。验证方法：

```bash
# SNI 填 IP —— 通，返回真实数据
curl -sk https://<公网IP>/api/v1/stats
# SNI 填域名 —— 被掐
curl -v https://www.relx5th.space/api/v1/stats    # Recv failure: Connection was reset
```

备案下来之前只能临时走 `http://<公网IP>`（HTTP + 裸 IP，明文）。备案通过后把 `config.json` 的 `stats_api_base` 换成上面的 HTTPS 域名即可，服务端证书和 nginx 已就绪，不用再动。

**踩过的三个坑**

1. **nginx 配置要放 `conf.d/`，别放 `sites-available/`**。后者归 nginx 包管理，我写好的配置加 symlink 之后整个目录被重置回出厂状态，配置被 `sites-enabled/default` 覆盖掉了，而目录时间戳没变，一时看不出来。`conf.d/*.conf` 不在包管理范围内。配置另存了一份在 `/root/nginx-autoticket-stats.conf.bak`。
2. **nginx 1.24 不认 `http2 on;`**，那是 1.25.1 的语法，1.24 得写成 `listen 443 ssl http2;`，写错直接 `unknown directive "http2"` 起不来。
3. **这台机器访问 Let's Encrypt 不稳定**：同一时段连续 3 次请求通常只有 1~2 次成功（TLS 握手本身正常，是跨境丢包），签证书和续期都得多等一会儿。续期是静默重试，建议 30 天后手动 `certbot renew --dry-run` 确认一次。注册时用了 `--register-unsafely-without-email`，没有邮箱就不会收到到期提醒，但自动续期照常工作。

**运维速查**

```bash
systemctl status autoticket-stats                    # 看状态
journalctl -u autoticket-stats -f                    # 实时日志（每个请求一行）
journalctl -u autoticket-stats -n 200 --no-pager     # 最近 200 行
systemctl restart autoticket-stats                   # 重启（已设开机自启）

nginx -t && systemctl reload nginx                   # 改 nginx 配置：先测语法再 reload
certbot renew --dry-run                              # 证书续期演练

curl https://www.relx5th.space/api/health               # 存活检查
curl -s http://127.0.0.1:8080/api/v1/stats           # 服务器上直连应用，绕过 nginx 和 DNS
```

**备份**（SQLite 热备，服务不用停）

服务器没装 `sqlite3` 命令行工具，用 Python 内置模块备份：

```bash
python3 -c "
import sqlite3
src = sqlite3.connect('/opt/stats/data/stats.db')
dst = sqlite3.connect('/root/stats-backup-\$(date +%F).db')
with dst: src.backup(dst)
dst.close(); src.close()
print('备份完成')
"
```

注意：直接 `cp` 会漏掉 `-wal` / `-shm` 文件导致数据不一致，要么用 `.backup`（上面的写法），要么停服务再复制整个 `/opt/stats/data/` 目录。
